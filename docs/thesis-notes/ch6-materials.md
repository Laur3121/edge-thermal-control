## 6.2 データ収集

### 計測項目(ノード側 `scripts/node/node_agent.py`、1 秒周期)

| 項目 | 取得元 | 単位・形式 | 用途 |
| --- | --- | --- | --- |
| CPU 温度 | `/sys/class/thermal/thermal_zone0/temp` | ℃(刻み約 0.49℃) | 観測値 y |
| CPU 使用率 | `/proc/stat` の前回との差分 | %(1 秒間の平均) | 負荷入力 u |
| コアごとの使用率 | 同上 | % | 確認用 |
| ARM クロック | `vcgencmd measure_clock arm` | Hz | スロットリングの確認 |
| スロットリング状態 | `vcgencmd get_throttled` | 16 進(0x0 なら無し) | スロットリングの確認 |
| ファン状態 | エージェント内部 | 0/1 | 操作量 f |
| ファン PWM | hwmon(pwmfan)の `pwm1` | 0〜255 | 実際に回っているかの確認 |
| PoE 電流 | hwmon(rpi_poe)の `curr1_input` | mA | 消費電力の目安 |
| 強制 ON 中か | エージェント内部 | 0/1 | 安全機能が動いたか |
| 負荷ワーカー数 | エージェント内部 | 0〜4 | 実験条件 |

- 送信:MQTT トピック `etc/<ノード名>/telemetry` に JSON で送る(QoS 0)。ノード側の CSV にも同じ内容を残す
- 受信:制御用 PC の `scripts/collector.py` が全ノード分を受けて `raw/telemetry.csv` に追記(受信時刻も記録)。**生ログは追記のみで上書きしない**
- 室温:`scripts/ambient_logger.py` が SwitchBot 温湿度計 4 台(ラックの上・左・右、離れた位置のハブ)を **60 秒ごと**に SwitchBot Web API から取得

### 「なぜ」を書くためのヒント(自分の言葉で)
- CPU 使用率を瞬時値ではなく **1 秒間の平均**にしたのはなぜ?(IPSJ の時に b が負になった原因の1つ。瞬時値だと何が起きる?)
- クロックとスロットリング状態を測るのはなぜ?(旧データでは 84℃ で頭打ちだった)
- 室温を測るのはなぜ?(同定実験の途中で室温が 1.6℃ 下がった。モデルは室温からの上昇分で立てている)

## 6.4 ファンの駆動(\label{sec:impl-fan})

| 項目 | 内容 |
| --- | --- |
| ファン | Raspberry Pi PoE+ HAT のファン |
| Linux 上の見え方 | 冷却デバイス(type = `pwm-fan`)。段階 0〜4 |
| ON/OFF の方法 | 冷却デバイスの `cur_state` に、ON なら最大段階、OFF なら 0 を書く |
| OS の自動制御 | 標準では `step_wise` 方式で、約 40℃ から回り始める → 実験中は `thermal_zone0` の policy を `user_space` にして止める。エージェント終了時に元に戻す(異常終了でも戻る) |
| 指令 | MQTT トピック `etc/<ノード名>/fan/set` に "0"/"1"(QoS 1)。制御用 PC は 2 秒ごとに送り直す |
| 安全機能 | ① CPU 温度が **82℃ 以上**なら強制 ON ② 指令が **10 秒以上途絶えたら**強制 ON(制御用 PC やネットワークが止まった場合) |
| 応答時間 | ファンを ON にすると **5 秒以内**に温度が下がり始める(`experiments/20261113_step_identify`) |
| 実行方法 | systemd サービス `etc-agent`(root 権限が必要なため。`scripts/node/install_node.sh`) |

### ヒント
- 安全機能の 82℃ は、Tlimit(80℃)より少し上。なぜ 80℃ ちょうどではない?(80℃ だと提案手法の判断より先に安全機能が動いてしまい、評価が混ざる)
- 指令が途絶えたら「OFF」ではなく「ON」にするのはなぜ?(どちらに倒すと安全か)
- 6.1 の最後の「制御用 PC が停止した場合の対策は 6.4 節で述べる」の答えがここ

## 6.5 負荷生成と実験の自動化

| 項目 | 内容 |
| --- | --- |
| 負荷 | `stress-ng --cpu N`(N = 0〜4 コア)。MQTT トピック `etc/<ノード名>/load/set` に N を送る |
| CPU 周波数 | 実験中はガバナを `performance` に固定(標準の `ondemand` だとアイドル時のクロックが 0.7〜1.7 GHz で変わり、発熱が変わるため)。終了時に `ondemand` に戻す |
| シナリオ | JSON で「段階」を並べる。各段階に負荷・ファン・長さ(秒)を書く。「A が 75℃ になるまで」のような条件付きの段階、繰り返しも書ける |
| 開始前の待ち | 全ノードの温度の傾きが直近 120 秒で **0.2℃/分以下**になるまで待つ(最大 30 分)。前の実験の熱が残らないように |
| 記録 | 段階の切り替え時刻を `events.csv`、シナリオを `config.json` として実験ディレクトリに保存。収集と室温の記録も自動で起動 |
| 実行 | `scripts/run_experiment.py`(制御用 PC) |

### ヒント
- 実験を手動ではなくスクリプトで回すのはなぜ?(条件の再現性。比較実験で全条件を同じ負荷パターンにする必要がある)
- 開始前に温度が落ち着くのを待つのはなぜ?
