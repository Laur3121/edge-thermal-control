# 実験の厳しめのレビュー(2026-11-27、予備審査のあと)

予備審査では伝え方の問題が大きく、実験の中身は審査員に見てもらえなかった。1 月の本審査で初めて突かれる前に、Claude が審査員のつもりで実験を見直した。
本筋(① 囲いの蓄熱が主因で H 1 つで表せる → ② H で温度計なしに予測できる → ③ 速いファンでは予測は不要、冷却が遅いほど効く)の根拠ごとに、「突かれる点」「今の根拠」「どう潰すか」を書く。

どう潰すかの種類:**実験**(12 月に測る)/**解析**(今あるデータでできる)/**限界**(論文に限界として書く)/**口頭**(質問への答えを用意する。本文は 1 文まで)

## 一番の弱点(先にこれ)

1. **③ は「しきい値を下げれば済むのでは」に実機で答えていない。** 遅れ 60 秒の実機(open_delay60)は、しきい値 75/70℃ と提案 α = 2 を 1 組ずつ比べただけ。提案は 80℃ 超えを 3 割減らしたが、稼働は +3.8 ポイント多い。これは「同じ稼働でより安全」でも「同じ安全で稼働が少ない」でもなく、交換関係の上の別の点かもしれない。しきい値を 70℃ に下げても同じくらい減るなら、予測の意味はない。シミュレーションは設定を振った曲線で答えていた(最小稼働率)が、実機はしていない
2. **② と ③ がつながっていない。** 制御の実験では、提案(KF + H)と自ノードの予測(H なし)の差が一度も出ていない(11/14、11/25 箱、11/26 開いた状態、シミュレーション)。③ の効果は「予測を使うこと」から来ていて、H からではない。題目の「空間熱干渉を考慮した」が制御の成果に効いていないと言われる
3. **② の「誤差 4〜5 割減」は比べる相手が弱い。** 相手は「部屋の室温を基準にした自ノードのモデル」。温度の履歴だけの AR は提案と同じ精度(箱の上段 0.43 対 0.44℃、8 台では AR の方が良い 0.51 対 0.60℃)。H の意味を「ファンを OFF にしたら何℃ かを予測できること」に置き換えたが、その予測が当たることは示していない

4. **(11/28 追記。最初のレビューで書き落とした)動的マージンが働いていない。** σ は実機でほぼ一定(約 0.84℃)で、M = ασ + δ は実際には固定マージン。80℃ 超えの原因(負荷の急な上昇、予測のずれ +12〜17℃)を σ はまったく表さない。11/14 から分かっていたのに、このレビューの「一番の弱点」に入れず、実験 A で δ を振るときもこの食い違いを言わなかった(レオに指摘された)。対応:負荷が上がる確率を入れた動的マージンをシミュレーションで試す(だめなら、動的マージンは成果として言わず、マージンは同定データのルールで決める)

この 3 つは 12 月の実験で潰せる(下の「12 月の実験の優先順位」)。

## ① 囲いの蓄熱が主因

| 突かれる点 | 今の根拠 | どう潰すか |
|---|---|---|
| 「直接の排熱は 1℃ 未満」は、測れる精度より小さいのでは | 開いた状態では、負荷をかけていないノードの「上昇」がブロックごとに −1.5〜+2℃ 散らばる(部屋とラックの空気の動き)。1℃ の判定より揺れが大きい。箱の中では揺れが ±0.5℃ に収まり、そこでも 0.5℃ 未満 | **限界**+言い方を変える:「開いた状態では 1.5℃ の揺れより小さく、箱の中では 0.5℃ 未満」。「ない」とは言わない |
| 囲いの条件が途中で変わった、1 回しか測っていない | 閉じた箱はアイドルで 40℃ に迫り中止 → 前面を開け、さらに上段も出した(落ち着き待ちの間、負荷のブロックの前)。箱・開いた状態とも 1 回ずつ、同じ日の続けて | **実験**:囲いあり・なしを日を変えてもう 1〜2 回。ブロックは「1 台だけ負荷」と「8 台負荷」の 2 つに絞って短くする |
| 「囲うと +5〜9℃」は、別の時刻の比較 | 開いた状態と箱は同じ日の別の時間帯。部屋の差 3.7℃ を引いた値 | 上と同じ実験で、同じ日に交互に測る(開→箱→開) |
| 段ボールで囲うのは、IPSJ のタオルと同じで都合のいい条件では | 「収納棚・筐体の中」に当たる、と説明しているだけ。現実の筐体の寸法・開口と比べていない | **限界**+**口頭**:囲いは干渉を作るためではなく「熱がどこから来るか」を分けるための条件。囲いなしの結果も全部出している。現実の筐体(屋外ボックスなど)の開口率を 1 例調べて並べる |
| ファンの種類・風量・風向きが分からない | 予備審査で指摘済み | **L**:型番と風量を調べ、吸気・排気の向きを目で確かめる |
| 計測プログラム自体が温度を上げていないか | 未測定 | **実験**(短い):計測あり/なしでアイドルの温度を比べる |

## ② H で温度計なしに予測できる

| 突かれる点 | 今の根拠 | どう潰すか |
|---|---|---|
| 比べる相手が弱い(上の 3) | AR と同じ精度 | **言い方を変える**:「部屋の温度計しかないとき、箱の中の温度計を足したのと同じ精度(0.44 対 0.41℃)」が主張。AR とは同じ精度と正直に書く |
| H は「空間熱干渉」ではなく、ゆっくり動くずれ(バイアス)を推定しているだけでは | ρ は 0.995(探索範囲の上限)の台が多い。r2・r6 は c < 0 で H を外した。H の時定数は数分〜それ以上で、隣の負荷よりラック全体の温まりを拾っている | **言い方を変える**:H は「囲いの中の熱のたまり」。① の結果(熱は囲いにたまる)と合っているので、むしろ ① から ② への筋になる。「隣の排熱を推定」とは言わない。ρ が上限に張り付くことは限界に書く |
| 評価の分け方を結果を見てから変えた | 実行前の分け方(前半で同定)は上段に負荷がなく設計の誤り → 後半で同定・前半で評価に入れ替えた | **限界**:入れ替えたことと理由を本文に書く(すでに README にある)。12 月の実験では、同定の区間に全ノードの負荷が入るよう実行前に確かめる |
| 「ファン OFF なら何℃ か」の予測が当たることを示していない | ない。評価はファン OFF の区間だけ | **解析**:open_control・delay60 のデータで、ファンを止めた直後(OFF にした判断の後)の実測と、その時点の「OFF のまま」の予測を比べる |
| 0.4℃ 良くなって何が嬉しいのか | マージン M = 2σ + 0.5 なので、σ が小さいと 80℃ ぎりぎりまで待てる…という理屈だけ | 下の 12 月の実験 B(H が制御で効くか)で答える。効かなければ「推定としての成果」に留める |

## ③ 速いファンでは予測は不要、冷却が遅いほど効く

| 突かれる点 | 今の根拠 | どう潰すか |
|---|---|---|
| しきい値を下げれば済むのでは(上の 1) | 実機は 1 組の設定どうしの比較 | **実験 A**(下) |
| 60 秒の遅れは、ソフトで指令を遅らせただけ。そんな装置はあるのか | 「60 秒は実際の装置で測った遅れではない」と README に書いてある。例として空調で冷やす小さなサーバ室(笹倉ら 2020) | **限界**+**口頭**:遅れは「冷却の性質」の代わり。実際の値の例を文献か実測で 1 つ示す(SwitchBot のサーキュレーターで部屋の空気が動くまでの秒数を測るのが一番早い) |
| 実際の遅い冷却は「むだ時間」より「1 次遅れ」では。その場合シミュレーションでははっきりしなかった | 1 次遅れは実行前の判断で効果がはっきりせず、効いたのは結果を見た後に足した「ぎりぎりまで待つ判断」 | **限界**:むだ時間だけを主の結果にする。1 次遅れは今後の課題。後から足した判断は主の結果に使わない(今の方針どおり) |
| 実機では提案も 80℃ を超えた。シミュレーションでは超えなかった | 超えた原因の多くは、負荷が低いうちに 4 コアへ上がること(今の負荷が続くと仮定しているため) | **口頭**:未来の負荷を知らない限り、遅れの分は避けられない。シミュレーションとの違いは 12 月に確かめる(モデルが実機より温まるのが遅い可能性) |
| 2 巡・1 晩だけ。偶然では | delay60 は 14 組すべてで提案の方が短い | **実験**:delay_sweep を日を変えてもう 2 回(tasks の計画どおり) |
| 80℃ を超えても、クロックはほとんど下がっていない。何が困るのか | クロックの平均の低下は 0.05% 未満(82℃ の強制 ON が先に入るため) | **口頭**:80℃ は Raspberry Pi がソフトで温度制限を始める温度で、本研究はそれを「守る上限」と定義した。超えても止まらないのは 82℃ の安全装置のおかげで、その安全装置に頼らずに済むかを見ている。本文に 1 文 |

## 12 月の実験の優先順位(本筋に効く順)

今動いている delay_sweep(遅れ 0・15・30・60 秒)はそのまま回す。その後に足すもの:

- **A. 遅れありで、しきい値の設定を振る(③)。**(11/27 に計画・待機済み:experiments/20261127_tradeoff。提案は α でなく δ を振る) 遅れ 60 秒と 30 秒で、しきい値 T_on = 65・70・75℃(T_off = T_on − 5)と提案 α = 1・2・3。各設定 2 巡。図は「稼働率 対 80℃ 超え時間」の点を並べた交換関係。提案の点が、しきい値の点を結んだ線より左下にあれば「予測の意味がある」。なければ、そう書く
- **B. H が制御で効くか(② → ③ のつなぎ)。** 囲いあり + 遅れ 60 秒で、提案(KF + H)と自ノードの予測(H なし、部屋の室温)を比べる。囲いの中では自ノードの予測の誤差が提案より 0.4℃ 大きい(30 秒先 MAE 0.84 対 0.44℃)ので、遅れがあるとその差が 80℃ 超えに出るはず。出なければ「H の成果は推定まで」と書く
- **C. 繰り返し。** A・B と delay_sweep を日を変えて。①の囲いあり・なしの比較も短くしてもう 1〜2 回
- **D. 小さいもの。** 計測の影響(アイドルで計測あり/なし)、遅れの実例(サーキュレーター)、ファンの仕様(L)

どれも、実行前に条件・判定・予想を README に書き、結果しだいの次の実験も先に決めてから回す。
