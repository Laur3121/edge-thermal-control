## 0. この振り返りのために確かめたこと

遅い冷却のシミュレーションの「最小稼働率」は、パターンごとに後から設定を選んだ値で、甘い。そこで2つ確かめた(`results.csv` から計算、新しい実行はなし)。

- **余裕を残した指標(最高 78℃ 以下での最小稼働率、4 パターン平均)**:予測の優位は残る。むだ時間 30 秒で 予測 18.4% / しきい値 31.3%、60 秒で 23.5 / 48.2%。1 次遅れでも、事前に決めた判断のままで 120 秒で 20.8 / 34.0% と差が出た(80℃ ぎりぎりの比較では差がはっきりしなかったもの)
- **設定の使い回し(比較パターンで選んだ設定を、ランダム 3 本にそのまま使う)**:むだ時間 15 秒以上では、**予測もしきい値も 3 本中 2〜3 本で 80℃ を超えた**(遅れ 0 では予測 0 本、しきい値 2 本)。1 次遅れでは、予測は 0 本、しきい値は 1〜3 本で超えた
  - 意味:ぎりぎりに合わせた設定は、負荷のパターンが変わると守れない。予測の σ が「負荷が変わる不確かさ」を含んでいないことと同じ問題(下の 1-2)

### 1-1. OS 標準のファン制御との比較がない【一番聞かれそう】→ 11/22 21:20 から実験中(experiments/20261122_compare_os、OS 標準・しきい値・提案 × 3 巡、ラテン方格)

- 提案:比較実験と同じ 20 分のパターンを、OS 標準のままで 3 台 × 3 回(約 1 時間)。指標は ON の時間に加えて、段階で重みをつけた稼働(段階 2 は最大の何割か)
- 注意:OS 標準は低い段階で回すので、「ON の時間」だけで比べると不公平。騒音・寿命の面では低い段階の方が有利かもしれない → 段階ごとの回転数か騒音を測ると公平になる

### 1-2. 「動的マージン」が動的でない → 11/22 済(experiments/20261122_risk_margin):切り替えの確率を含めたマージンで A は判定を満たす、B・C は満たさず(3 台中 1 台)。8 章に記載
- 干渉がない(c = 0)と σ は一定。誤差の大半は負荷の切り替え(30 秒以内)から来るのに、σ はそれを含まない
- 提案(オフラインでできる):負荷の変化の大きさで温度のプロセスノイズを増やす(qT(t) = qT0 + γ|u_t − u_{t−1}|、H の適応ノイズと同じ形)、または「負荷が上がる確率」を過去の負荷の切り替えの頻度から見積もってマージンに足す
- 評価:ランダムの実験の前半で γ を決め、後半で超過率とマージンを見る(同定と評価を分ける)。条件は先に決める
- 11/14 に「すぐ最大の負荷に上がる」と仮定したらマージン 6〜8℃ で過剰だった。確率で重みをつける中間の方法が残っている
- これが効けば「動的マージン」という題目の看板が守れる。効かなくても正直に書ける

## 2. 12 月の実験(やり直し・追加)

優先度の高い順。

1. **囲った環境での干渉と H の効果**【題目に関わる】:今のままだと「空間熱干渉を考慮した状態推定」の効果を示すデータが一つもない。IPSJ の容器(密閉プラスチック)で、条件を先に決めて、干渉の大きさと、H ありなしの予測と制御を比べる。囲いではファンの効きも変わる(熱がこもる)ので、遅い冷却の実機版にもなる
2. **効きの遅い冷却の実機**:SwitchBot のサーキュレーター(部屋のファン)を操作量にする。クラウド API の遅れ + 風が届く時間で、シミュレーションの境界(15〜30 秒)を実機で確かめる
3. **ファンを回した状態での干渉、全台に負荷をかけたときの干渉**:今の RQ1 は「A だけ 2 コア、ファンは全部 OFF、10 分」の1条件。ファンの風で排熱が隣に流れる可能性は確かめていない
4. **8 台・縦の配置**:熱は上に昇るので、上下の段で干渉が出る可能性がある
5. **実アプリの負荷**(ffmpeg の動画変換など)と OS 標準との比較(1-1 を 1 晩でやらなければここで)
6. **比較実験の再現**:今は 1 晩だけ。別の日(室温が違う日)にもう 1 晩やると、「日によって変わらない」が言える
7. **ファンの段階を使う制御**:今は ON = 最大の段階 4 だけ。段階 1〜2 で足りる場面が多いはず。騒音・寿命の面では段階を下げる方が効く可能性
8. **騒音の計測**:「騒音を減らす」を理由に挙げているので、スマホのアプリでもよいので段階ごとの dB を測っておくと根拠になる

## 3. 手法・モデルで気になる所

- **ファンのモデル**:物理的にはファンは熱抵抗 R を変える(掛け算)が、加算項 e·f で表している。検証区間で案B の方が誤差が小さかったので選んだが、負荷が高いときにファンの効きが大きくなる(掛け算の性質)を表せない。負荷の大きさごとに残差を見ると確かめられる
- **1 次のモデル**:ファン ON の直後は数秒で数℃下がり、その後ゆっくり下がる(5.3 節)。速い部分(CPU のダイ)と遅い部分(ヒートシンク)の 2 つの時定数がある可能性。2 次のモデルにすると切り替えの誤差が減るかもしれない
- **パラメータの日による違い**:A の時定数が 11/13 は 66 秒、11/14 は 96 秒。運用ではオンラインで同定し直す仕組みが要る(カルマンフィルタでパラメータも推定する、または逐次最小二乗)
- **self_fixed のマージン**:同定データの誤差の 97.7% 分位点で、切り替えの誤差も含むので大きめ(稼働 45%)。比較相手として弱く見えるので、分位点を変えた曲線(シミュレーションで済んでいる)を示して公平さを説明できるようにしておく
- **稼働率の定義**:指令の ON の割合。ファンが実際に回っていた時間(回転数)とは確かめていない。PoE+ HAT のファンの回転数が読めるなら(tach)、確かめる
