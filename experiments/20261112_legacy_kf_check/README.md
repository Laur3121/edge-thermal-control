# 2026-11-12 旧データ(実験C)での KF 再実装の動作確認

新しい実験ではない。`data/legacy/` の実験C(2台、IPSJ 時点)に、再実装したコード(`src/etc/`)を通したオフライン解析。
目的はコードが最後まで動くことの確認と、旧データの限界の把握(タスク A4)。予稿の数値の再現は目標にしていない。

## 実行方法

```sh
python scripts/eval_offline.py \
  --target data/legacy/expC_2nodes_raspi2_2026-04-16.csv \
  --neighbor data/legacy/expC_2nodes_raspi1_2026-04-16.csv \
  --out experiments/20261112_legacy_kf_check/raspi2_target
# raspi1_target は target と neighbor を入れ替えたもの
```

既定値:dt = ログの中央値(5.10秒)、Δ = 30秒(6ステップ)、先頭60%を同定・残り40%を評価、80℃以上の遷移は同定に使わない、
R = 0.077 / qH0 = 0.008 / β = 2.0 / α = 2.0 / δ = 0.5(IPSJ の値)、qT は残差から逆算。各ディレクトリの `params.json` に全設定と同定結果。

## 結果

コードは最後まで動き、合成データのテスト(`tests/test_synthetic.py`:同定でパラメータが戻る、σ が実際の誤差と合う、H ありが H なしより良い)は通る。
しかし **旧データではパラメータが物理的に意味のある値にならない。**

| 対象 | モデル | a | b | c | 問題 |
| --- | --- | --- | --- | --- | --- |
| raspi2 | Self-only | 1.051 | −1.04 | — | a > 1(時定数が定義できない)、b < 0 |
| raspi2 | H あり | 0.958 | −0.82 | 0.60 | b < 0、ρ が探索範囲の上限 0.995(τ_H ≈ 1000秒) |
| raspi1 | Self-only | 0.936 | −2.11 | — | b < 0 |
| raspi1 | H あり | 0.894 | −1.91 | 0.73 | b < 0、ρ が上限 |

CPU 使用率を過去30秒・60秒の移動平均にしても(`--u-smooth`)b は負のまま。

予測精度(評価区間)も提案手法が最良にはならず、提案手法のマージンは 8〜19℃ と過大(雑音の見積もりが大きいため σ が膨らむ)。

## 原因

1. **CPU 使用率が瞬時値**:5秒ごとのログに、その瞬間の値(0 か 100 に近い値)が記録されている。50% 一定のはずの負荷が雑音だらけになり、b が決まらない
2. **同定に使える区間で負荷が変わらない**:80℃ 未満の区間は raspi1 では最初の数分だけで、その間ずっと負荷がかかっている。負荷の ON/OFF がないので b と d を分けられない
3. **H が自分の負荷の効果を吸い込む**:ρ が上限に張り付き、H がゆっくりしたトレンド項として働いている(図の中段で、自分の負荷開始と同時に H が跳ねる)
4. raspi2 はアイドル中も隣の熱で温度が上がり続けるため、Self-only では a > 1 になる(干渉がある証拠でもある)
5. 室温が記録されていない

なお IPSJ 版 `predict_rc.py` は Δ秒先の予測に **未来の CPU 使用率と隣接温度の実測値** を使っていた(本実装は「今の値が続く」と仮定)。予稿の数値と比べるときはこの差に注意。

## 新しい実験への反映

- 収集(A6):CPU 使用率は「前回の取得からの平均」(`/proc/stat` の差分)で記録する。瞬時値は使わない
- 同定(B1・B2):80℃ 未満で、負荷 ON/OFF のステップを含む専用の実験を行う(ファン常時 ON か、負荷を軽くしてスロットリングを避ける)
- ρ の探索範囲と、同定区間の長さ(τ_H を決めるには τ_H の数倍の長さが必要)を確認する
- 室温を記録する
