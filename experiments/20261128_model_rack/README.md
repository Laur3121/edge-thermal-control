# model_rack(ラック全体を同時に計算するモデルで、予測のずれが直るか。オフライン)

実機の実験ではない。2026-11-28 夜。条件と判定は、この README を書いた時点(実行前)で決めた。結果は外れても書く。

## なぜやるか(本筋のどこか)

② と ③。open_delay60 では、負荷が一定でファン OFF の 90 秒でも、提案の予測は実測より 1.6℃ 低かった(中央値)。シミュレーション(実機役 = 自ノードのモデル)では、しきい値は実機を再現したが、提案は実機の方が約 2 倍悪かった。
レオの指摘(11/28):分かっていること(場所による干渉の違い、ラック全体の温まり)をもっと入れて、数値で計算すれば良くなるのでは。
仮説(Claude):今の H は「隣の温度は先読みの間このまま」と仮定する。8 台が同時に温まるときは隣も温まり続けるので、その分だけ低く予測する。全台のモデルを同時に回せば直る。

## 方法

- θ = T − 室温(ハブ 2)、5 秒ごと。スロットリング中(クロック 1790 MHz 未満)を含む遷移は除く
- 比べる予測(どれも、その時刻までの実測だけから。負荷とファンは先読みの間いまの値が続くと仮定)
  - **P0 自ノード**:θ' = aθ + bu + ef + d(control_params_open.json の self)
  - **P1 今の提案**:control_params_open.json の withH を KF で回す(隣 = 縦・横・斜めで接するノードの平均、先読みの間は隣の温度を今の値のまま)
  - **P2 ラック同時**:台ごとに θ_i' = a_i θ_i + b_i u_i + e_i f_i + g_i θ̄_{−i} + d_i(θ̄_{−i} = 自分以外の 7 台の θ の平均。g_i が場所による違い)。先読みでは 8 台を同時に回し、θ̄ も一緒に進める(隣も温まり続けるのを計算に入れる)
  - **P2n ラック同時(隣だけ)**:P2 の θ̄ を縦・横・斜めで接するノードの平均にしたもの
- 同定(P2・P2n):`20261125_pattern_open` 全区間 + `20261126_open_ident` 全区間(11/25〜26、囲いなし、最小二乗)。P0・P1 は今の制御と同じ control_params_open.json
- 評価:**別の日**(11/28)の `20261127_delay_sweep/d60`・`d30`・`20261127_tradeoff/d60`(囲いなし、制御の実験)。r5 は除く
- 評価する時刻:その後 90 秒の間、自分の負荷がほぼ一定(上がり 0.2 未満)で、自分のファンも OFF のまま(open_delay60 の分析と同じ)。指標は「90 秒の間の実際の最高 − 予測の最高」の中央値(ずれ)と、90 秒先の平均絶対誤差(MAE)。30 秒先の MAE も出す

## 判定(実行前に決めた)

- **P2(または P2n)で直る**:ずれの中央値の絶対値が 0.5℃ 以下、かつ 90 秒先の MAE が P1 の 0.8 倍以下
- **一部直る**:どちらか一方だけ
- **直らない**:どちらも満たさない
- 直る・一部直るなら、P2 を制御(負荷リスクの動的マージンと組み合わせて)に入れる。直らないなら、ずれの原因は別(ファンの効き方、日による違いなど)として、次の候補(ファンの効きを温度差に比例させる、など)を同じ形で試す

## 結果(2026-11-28 夜)

`eval_rack.py` → `results/errors.csv`・`summary.csv`。評価した時刻 20087(台・時刻)。

| 予測 | ずれの中央値(最高)[℃] | 90 秒先 MAE | 90 秒先 平均誤差 | 30 秒先 MAE |
|---|---|---|---|---|
| P0 自ノード | 0.49 | 2.21 | 1.68 | 1.17 |
| P1 今の提案(KF + H) | 0.40 | **1.58** | 0.90 | **0.90** |
| P2 ラック同時(7 台の平均) | 0.49 | 2.16 | 1.60 | 1.16 |
| P2n ラック同時(隣だけ) | 0.49 | 2.17 | 1.69 | 1.16 |

- 判定の機械的な結果は P2・P2n とも「一部直る」(ずれ 0.49 ≤ 0.5、MAE 比 1.37)。**ただし、ずれの基準は何もしていない P0 でも満たしており、基準の作り方が悪かった。MAE は P1 より 37% 悪い。実質は「直らない」と判断し、P2 は制御に入れない**(実行前の決まり「一部直るなら制御に入れる」には従わない。理由はこのとおり)
- 仮説(隣が温まり続けるのを入れれば直る)は外れ。g(他の台の平均の係数)は 0.01〜0.03 と小さい
- 台ごとの 90 秒先の平均誤差(P0 / P1):r4 +5.9 / +1.9、r8 +3.1 / +2.7、r1 +1.8 / +1.8、r2 +0.8 / +0.8、r6・r7 ほぼ 0、r3 −0.6 / −1.0。**ずれの大部分は、同定した日(11/25〜26)と評価した日(11/28)で台ごとのモデルがずれていること**。P1 が一番良いのは、KF が実測で H を直し、日によるずれの一部を吸収するため
- 訂正:open_delay60 の「1.6℃ 低い」は、提案が OFF と判断した時刻(80℃ に近い所)だけを選んだ値。負荷一定・ファン OFF の時刻全体ではずれの中央値は 0.4℃

## 追加:H の追いつく速さ(qH0)を上げる(2026-11-28 夜、実行前に決めた)

- 日によるずれを KF の H が吸収しているなら、H のプロセスノイズ qH0 を大きくすると早く追いつき、誤差が減るはず
- P1 の qH0 を 0.008(今)→ 0.08、0.8、8 にして、同じ評価をする。β(隣の急変で qH を上げる係数)は 2.0 のまま
- 判定:90 秒先の MAE が今の P1(1.58℃)の 0.8 倍以下(1.26℃ 以下)になる qH0 があれば「追いつく速さで直る」→ 制御に入れる候補。なければ「直らない」→ 日によるずれは、制御の直前に短い同定をやり直す(または限界として書く)
- 注意:qH0 を大きくすると σ も大きくなり、マージンが広がる(稼働が増える)。予測の当たりだけでなく σ の大きさも書く


### qH0 の結果

`eval_qh.py` → `results/qh_sweep.csv`。

| qH0 | 90 秒先 MAE | 90 秒先 平均誤差 | 30 秒先 MAE | 30 秒先の σ |
|---|---|---|---|---|
| 0.008(今) | 1.58 | 0.90 | 0.90 | 0.74 |
| 0.08 | 1.56 | 0.88 | 0.89 | 0.75 |
| 0.8 | 1.45 | 0.77 | 0.81 | 0.78 |
| 8 | 1.32 | 0.62 | 0.71 | 0.98 |

- 判定:1.26℃ 以下にならない → **直らない**。qH0 を上げるほど良くなる向きだが、決めた範囲を結果を見てから広げることはしない。σ も 0.74 → 0.98℃ に増える

## 追加 2:同定データに HAT なしの時期が入っていた(2026-11-28 夜、実行前に決めた)

- control_params_open.json の同定には 11/25 朝の `20261125_pattern_open` が入っているが、そのとき r4・r5・r8 には PoE+ HAT が付いていなかった(USB-C 給電、ファンなし。HAT を付けたのは 11/25 夜)。HAT 自体の発熱やファンの有無で温まり方が変わるので、r4・r8 のモデルがずれている可能性がある(r4 +1.9、r8 +2.7℃ のずれ)
- 確かめ方:HAT を付けた後の `20261126_open_ident` だけで自ノードのモデル(P0 と同じ形、ファンの項あり)を同定し直し、同じ評価をする(P0' とする)
- 判定:r4・r8 の 90 秒先の平均誤差の絶対値が、P0 の値(5.9・3.1℃)から 1℃ 以下になれば「HAT なしのデータが原因」。そうなら、パラメータは HAT を付けた後のデータだけで同定し直す(本番の撮り直しでは、同じ日の同定を使う)

`eval_hat.py` → `results/hat_refit.csv`。台ごとの 90 秒先の平均誤差 [℃](P0 = 今の self、P0' = open_ident だけで同定し直したもの):

|---|---|---|---|---|---|---|---|---|

- 同定し直すと、全台が一様に約 +2℃ 低く予測するようになった。open_ident(11/26 昼)と評価(11/28)の間に、部屋の温度計を引いても残る、日ごとの約 2℃ のずれがある。open_ident は箱を外した直後に行ったので、ラックとその周りがまだ冷えていく途中だった可能性がある(未確認)

## まとめ(11/28 夜)

- 予測のずれの主な原因は、モデルの式の足りなさ(隣の温まり、HAT の有無)ではなく、**同定した日と使う日で、台ごとに数℃ずれること**(部屋の温度計では取れない)
- 今の KF + H は、実測で H を直していくので、このずれを一部吸収している(だから P1 が一番良い)
- 対策の候補:本番では制御の直前に同じ日のデータで同定する(撮り直しの計画に入れる)。または、運用中に少しずつ同定し直す(今後の課題)
