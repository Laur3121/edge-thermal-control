# sim_slow_cooling(冷却の効きの遅さを変えたシミュレーション)

実機の実験ではない。`scripts/sim_slow_cooling.py`。11/14 の `20261114_sim_tradeoff` に「ファンの効きの遅れ」を足したもの。

## 問い

PoE+ HAT のファン(5 秒以内に効く)では、予測を使う方式としきい値方式の差がほぼなかった(第 7・8 章)。
「効くまでに時間がかかる冷却なら予測が有効になる」という仮説を確かめ、どの程度の遅さから差が出るかを調べる。

## 条件(2026-11-22、結果を見る前に決めた)

共通(sim_tradeoff と同じ):
- 対象:ノード A。実機役(plant)= 11/13 のステップ実験(案B)、制御器のモデル = 11/14 夜間データ(`scripts/control_params.json` の raspi1)。別のデータで同定したモデルどうし
- ノイズ:プロセス qT、観測 R は 11/14 の値。seed 固定、全方式・全条件で同じ乱数
- 室温 20℃、Tlimit 80℃、最小 ON 30 秒、ヒステリシス 1℃、制御周期 5 秒
- 負荷:比較実験と同じパターン(20 分)と、ランダム 3 本(区間 2〜10 分、0〜4 コア、各 3 時間)
- 冷却の強さ(ファンの係数 e)は変えない。変えるのは効くまでの時間だけ

遅れの入れ方(2 種類):
1. **むだ時間 L** = 0, 15, 30, 60, 90, 120 秒:ON/OFF の指令が L 秒後に効き始める(L = 0 が今のファン。判断は次の 5 秒区間から効くので、実際は L + 5 秒)
2. **1 次遅れ τ_f** = 0, 30, 60, 120, 240 秒:冷却の効きが時定数 τ_f でゆっくり立ち上がる・下がる(部屋の空調のようなもの)

制御器は遅れを知っているとする(予測を使う方式に公平にするため):
- 予測の先読み Δ = 30 秒 + L(むだ時間)、または 30 秒 + τ_f(1 次遅れ)
- 予測は「今の指令から先は OFF にしたら」。すでに出した指令(むだ時間の間に効くもの)や、冷却の残り(1 次遅れ)は予測に含める
- 判断には先読みの間の予測温度の最大値を使う(遅れがないときは今までの方式と同じ結果になる)
- カルマンフィルタと ARX の入力には、実際に効いている冷却の量を使う
- しきい値方式は今の温度だけを見る(遅れを知っていても使い道がない)

動かす設定(曲線にする。範囲は遅れが大きいときに備えて sim_tradeoff より広げた):
- threshold:T_on = 40〜79℃(T_off = T_on − 5)
- self_fixed:固定マージン 0〜20℃(0.5 刻み)
- proposed:α = 0〜12(0.25 刻み、δ = 0.5)

指標と判定:
- 各条件・各方式・各パターンで、80℃ を一度も超えない設定のうち、ファン稼働率が最も低いもの(「最小稼働率」)
  - 設定はパターンごとに後から選ぶことになるが、3 方式に同じ扱いをする。曲線(図)も全部載せる
- 「予測が有効」と判定する条件:予測を使う方式の最小稼働率が、しきい値方式より 5 ポイント以上低い。または、しきい値方式では 80℃ を超えない設定がない。比較パターンとランダム 3 本のうち、何本で成り立つかを書く
- 結果は全条件を載せる。仮説に合わない結果も書く

## 結果(2026-11-22 実行)

ファイル:`results.csv`(全点)、`summary.csv`(最小稼働率と判定)、`best_settings.csv`(最小稼働率を与えた設定)、図は `thesis/figures/fig_slow_cooling.png`(4 パターンの平均)。
遅れ 0 の結果は sim_tradeoff(11/14)と一致することを確かめた(同じ設定で稼働率・最高温度が一致)。

### まとめ

- **むだ時間(事前に決めた判断)**:遅れ 0 では差が 1〜5 ポイントで「有効」は 0/4(11/14 と同じ)。15 秒で 2/4、**30 秒以上でほぼすべてのパターンで有効**(30 秒:4/4、差 6〜13 ポイント。60 秒:4/4、差 14〜28 ポイント)。しきい値方式は遅れるほど「早めに回す」ためにしきい値を下げる必要があり、稼働率が大きく増える(平均 13% → 60 秒で 37%)。予測を使う方式の増え方は小さい(10% → 15%)
- **1 次遅れ(事前に決めた判断)**:効果ははっきりしない。有効は 30〜120 秒で 1/4、240 秒で 3/4。**240 秒の比較パターンでは、予測を使う方式の方がしきい値より 19 ポイント多かった**(仮説に合わない)
  - 原因:事前に決めた判断は「先読み 30 + τ 秒の間ずっと OFF にしたら」で判断する。τ が長いと先読みが長くなり(240 秒で 270 秒)、4 コアの負荷の間は「ずっと OFF なら必ず超える」と予測して、早くから回し続けてしまう。予測の当たり外れではなく、判断の仕方が悲観的すぎた
- **ぎりぎりまで待つ判断(事後の追加)**:「今は OFF、次の区間から ON にしても Tsafe を超えないか」で判断すると、1 次遅れでも遅いほど差が開き(120 秒で 3/4、240 秒で 4/4、差 12〜29 ポイント)、むだ時間でも同じ傾向になった。**この判断は事前の結果を見てから足したもの**なので、主の結果ではなく補足として扱う
- 提案と Self-only + 固定はほぼ同じ(c = 0 で σ が一定のため。11/14 と同じ)。差を生んでいるのは「予測を使うかどうか」で、σ の動的さではない
- むだ時間 120 秒・ランダム 1 は、開始直後の 4 コアの負荷でファンが効く前に超え、常時 ON でも 80℃ を超える(30 秒)。どの方式でも避けられないので判定から除いた(4 本中 3 本で判定)

### 解釈

- 仮説(「効きの遅い冷却では予測が有効」)は、むだ時間では事前に決めた判断のままで支持された。境界はおよそ **むだ時間 15〜30 秒**(PoE+ HAT の 5 秒の 3〜6 倍)
- 1 次遅れでは、予測の使い方(どういう「もしも」を予測して判断するか)によって結果が逆にもなる。遅い冷却ほど「ぎりぎりまで待つ」判断が必要で、これは判断の設計の問題として考察に書く
- 注意:最小稼働率は、各パターンで 80℃ を超えない設定のうち最も少ないものを後から選んだ値で、どの方式も最高温度は 79.5℃ 前後のぎりぎり。実運用で同じ設定を選べるわけではない。また、冷却の強さ(e)は PoE+ HAT と同じに固定しており、部屋の空調のように弱くて遅い冷却は試していない

## 確認の実行(2026-11-22 夜、条件は実行前に記録)

「ぎりぎりまで待つ判断」(rule = next)は、1 回目の結果を見てから足したので補足扱いにした。これを主の結果として扱えるかを、**1 回目に使っていない負荷パターン**で確かめる。

- 負荷:新しい乱数(seed 20261123)で作ったランダム 3 本(作り方は 1 回目と同じ。区間 2〜10 分、0〜4 コア、各 3 時間)。比較パターンは使わない(1 回目で見たため)
- 条件:1 次遅れ τ = 0, 30, 60, 120, 240 秒と、むだ時間 L = 0, 15, 30, 60, 90, 120 秒。判断は off(事前)と next(待つ)の両方。そのほかは 1 回目と同じ
- 判定(事前に決める):1 次遅れ 120 秒と 240 秒で、next の提案の最小稼働率がしきい値より 5 ポイント以上低いパターンが、それぞれ 3 本中 2 本以上なら、next の効果は確かめられたとする
- 余裕を残した指標(最高 78℃ 以下での最小稼働率)も合わせて出す
- スクリプト:`scripts/sim_slow_cooling_confirm.py`、出力:`confirm/`
