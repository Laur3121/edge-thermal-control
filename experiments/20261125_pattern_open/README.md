# pattern_open(干渉が起こる条件:開いた状態)

11/24 に先生から「干渉が起こるパターンを測っていないのは欠陥」と指摘された。これまでの干渉の確認(11/13 の 2 回、11/23)は、どれも上段に横に並べた 3 台だけだった。今回は 2 段のラックで、位置関係(縦・横・斜め)、熱量(1 台・下段 4 台・8 台)、ファン(風で排熱が飛ぶか、隣が熱いと冷えにくいか)を変えて測る。同じシナリオを段ボールで囲って回す(`20261125_pattern_box`)。
生ログ(raw/、events.csv)は編集しない。

## 条件(2026-11-25 朝、実行前に決めた)

- シナリオ:`scripts/scenarios/pattern.json`(`gen_pattern.py`、ブロックの中身は生成スクリプトの先頭)。約 3 時間 + 落ち着き待ち
- 配置:ラック(2 段 × 4 列、ボードは縦向き)。ポート側から見て

  ```
  上段: r1=raspi1[HAT] r2=raspi2[HAT] r3=raspi3[HAT] r4=raspi4
  下段: r5=raspi5      r6=raspi6[HAT] r7=raspi7[HAT] r8=raspi8
  ```
- HAT は手元に 5 個しかない(11/25 朝に分かった)。新しい 2 個は raspi6・7 に付けた。そのため、測定とファン制御は HAT のある 5 台(r1・r2・r3・r6・r7)。HAT のない 3 台(r4・r5・r8、USB-C 給電)は熱源として負荷だけかける(ファンなし、`--fan-mode none`。80℃ 超でクロックが下がるのは許す)
- 囲い:なし(ラックはむき出し)
- 負荷:`stress-ng --cpu 2`。負荷 600 秒 → 休み 720 秒(負荷 0・ファン OFF)
- ファン:PoE+ HAT、ON は段階 4。強制 ON は 82℃ 以上か指令途絶 10 秒
- CPU ガバナ performance
- 室温:SwitchBot(ラックの上=1、左=3、右=2、ハブ 2 は離れた場所=部屋)

## 指標と判定(実行前に決めた)

- 上昇 = 負荷の最後 60 秒の平均温度 − 負荷の直前 60 秒の平均温度 − 同じ時間の室温(ハブ 2)の変化(11/23 と同じ)
- **位置関係**(off_r6、off_r7):負荷をかけていない HAT ノードの上昇。1℃ 以上で「その位置関係で干渉あり」
  - 縦:off_r6 の r2、off_r7 の r3 / 横:off_r6 の r7、off_r7 の r6 / 斜め上:off_r6 の r1・r3、off_r7 の r2 / 遠い:off_r7 の r1
- **熱量**(off_bottom、off_all):off_bottom の上段 r1〜r3 の上昇(1℃ 以上で「下段の熱が上段に昇る」)。off_all は各ノードの上昇 − 自分だけ負荷のときの上昇(自分だけ:r6・r7 は off_r6・off_r7、r2 は cool_alone_load。r1・r3 は今回なし → 11/23 の値を参考に)
- **(a) ファンの風**:fanA_r6 の r2・r7・r1・r3 の上昇 − off_r6 の同じノードの上昇。1℃ 以上で「ファンの風で排熱が隣に届く」
- **(b) 冷却時の干渉**:r2 のファン ON の最後 60 秒の平均温度について、cool_nbrs − cool_alone(室温の変化を引く)。1℃ 以上で「隣が熱いと冷えにくい」。下がり幅(ファン ON 直前 60 秒 − 最後 60 秒)も並べる
  - 注意:cool_nbrs では、隣の HAT ノードが 82℃ に達して強制 ON になる可能性がある。その回数と時刻を events.csv から数えて書く
- 予想:横・斜め・遠いは 1℃ 未満(これまでと同じ)。縦は分からない(初めて測る)。(a)(b) は開いた状態では 1℃ 未満。段ボールでは全体の昇温が大きくなり、(b) が出やすいと考える

予想が外れても全部書く。

**読み方(判定を超えたものを、そのまま干渉とは言えない理由)**

- 負荷をかけていないノードの「上昇」が、同じブロックで −1.5〜+2℃ 散らばる。off_r6 では遠いノード(r4 −1.34)や隣(r3 −1.54、r7 −1.37)が下がり、off_r7 では遠いノードも含めて全台が +0.4〜+2℃ 上がった。負荷の前 5 分の傾きも、off_r6 の前は全台が下がり、off_r7 の前は全台が上がっていた。部屋(ハブ 2)は 3 時間で 17.0 → 19.8℃ と動き、ラックの上(温度計 1)は 22.8〜28.0℃ と動いた。ハブ 2 の変化を引いても、ラックの近くの空気の動きが残る
- 同じ方向でも逆向きで結果がそろわない(縦:r6→r2 は +0.06、r7→r3 は +1.95。横:r6→r7 は −1.37、r7→r6 は +1.26)。位置関係による違いより、ブロックごとのドリフトの方が大きい
- 試しに、同じブロックの遠いノードの平均を引くと(実行前には決めていない):off_r7 で r3 +1.5、r6 +0.8、r2 +0.5。off_r6 で r2 +0.7、r7 −0.7、r3 −0.9
- (a) の r3 +1.35 は、off_r6 の r3 が −1.54 だったことによる(引き算の相手が下がっていた)
- (b):ファン ON で下がる量は同じ(隣が休み 18.80℃、隣が負荷 18.85℃)。差 +2.98℃ は、ファン ON の時点ですでに 3℃ 高かった(75.8 → 78.9℃)ことがそのまま残ったもの。ファンの効きが弱まったのではない。ただし、負荷中の r2 は隣が負荷のとき最初の 1 分から 2〜3℃ 高い(図 `_cool`)。同じ「全台負荷」の off_all では r2 の上昇は自分だけのときと同じ(+19.3 vs +19.2)で、繰り返しの差が 2℃ ある

**判定とは別に見えたこと**

- ラック全体がゆっくり温まる:休みの温度が 3 時間で 4〜7℃ 上がった(r6 57 → 64℃、r3 56 → 61℃)。部屋は +2.8℃。12 分の休みでは元に戻らない

**予測の比較(30 秒先の MAE、`scripts/eval_pattern_pred.py`)**

- 実行前に決めた分け方(同定 = 前半、評価 = 後半)では、上段 r1〜r4 は同定区間で一度も負荷がかからず、負荷の係数が決まらない(MAE 7〜43℃)。設計の誤り。下段だけ見ると、① 0.61〜0.90、② 0.44〜0.76、③ 0.54〜0.70℃(r6 は ① − ② = 0.41)

## 温度の履歴だけの予測(AR)との比較(11/26 13:55、実行前に決めた)

先行研究(Coskun ら、ISLPED 2008)と同じ種類の、温度の履歴だけから予測する AR モデルを、Q2 と同じデータ・同じ分け方(--swap)・同じ評価時刻で比べる。`scripts/eval_pattern_ar.py`。11/22 の `20261122_ar_baseline` は囲いなし・3 台のデータだけだったので、囲いあり・なしの 8 台に広げる。
- AR:自ノードの温度 T(室温も負荷もファンも使わない)の差分 ΔT_t を、過去 p 個の差分で表す AR(p)(定数なし)。p は 1〜12 から同定区間の 1 ステップ先の残差の AIC が最小のもの。係数は同定区間(ファン OFF の遷移だけ)で最小二乗。30 秒先(6 ステップ)は差分を再帰的に予測して足す
- 指標:30 秒先の MAE(Q2 と同じ評価時刻、ファン ON を含む時刻は除く)。上段 r1〜r3 の平均と 8 台の平均。負荷中だけ・自分は休みで隣だけ負荷の時刻も
- 予想(Claude):AR は差分で予測するので、囲いによる温度の水準のずれ(部屋の室温を基準にするモデルが外れる原因)の影響を受けない。そのため、囲いありでも提案(KF + H)に近い精度(差 0.1℃ 以内)になる。負荷が切り替わる時刻は、負荷を入力に持つモデルより遅れる
- AR が提案と同じかそれより良くても、そのまま書く。その場合、H の意味は「ファンを OFF にしておいたら何℃ になるか」という入力を仮定した予測ができることと、囲いの熱の量を推定できること、と書き方を変える

### AR との比較の結果(11/26 14:00)

`results/pred_swap/ar_metrics.csv`。30 秒先の MAE [℃](Q2 と同じ評価時刻)。

| モデル | 囲いなし 上段 r1〜r3 | 囲いなし 8 台 | 囲いあり 上段 r1〜r3 | 囲いあり 8 台 |
|---|---|---|---|---|
| 自ノードだけ(部屋の室温) | 0.64 | 0.80 | 0.84 | 0.84 |
| 自ノードだけ(囲いの気温 = 温度計 2・3) | 0.71 | 0.86 | 0.41 | 0.50 |
| 提案(KF + H) | 0.39 | 0.64 | 0.44 | 0.60 |
| AR(温度の履歴だけ) | 0.38 | 0.51 | 0.43 | 0.51 |

- **予想どおり**、上段では AR は提案とほぼ同じ(差 0.01℃)。8 台の平均では AR の方が 0.09〜0.13℃ 小さかった(予想の「差 0.1℃ 以内」をやや超えた)
- 理由:評価区間(--swap)は、上段では「自分は休み・周りが負荷」の時刻が中心で、温度はゆっくり動く。差分で予測する AR は、部屋の室温を基準にしたときの水準のずれの影響を受けない
- **解釈**:30 秒先を「ただ当てる」だけなら、H がなくても温度の履歴だけの AR で同じ精度が出る。Q2 の「誤差 4〜5 割減」は、部屋の室温を基準にした自ノードのモデルとの比較であり、予測の方法として一番良いという意味ではない。H を持つ物理モデルの意味は、①「ファンを OFF にしておいたら何℃ か」という入力を仮定した予測ができる(AR は入力を持たないのでできない)、②囲いの熱の量(H)を推定できる、の 2 つと書く(実行前に決めたとおり)
